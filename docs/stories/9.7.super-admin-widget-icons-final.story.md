# 9.7: SuperAdminWidget, stato finale icone + regressione risolta

**Richiesta utente**: "migliora le 2 icone" -> "stile Marvel, outline, animazione,
fatti i 2 svg" -> "le icone non si vedono, studia i doc Filament icons/icon-button,
gli svg li autoregistriamo".

## Race multi-sessione (stesso prompt, piu' sessioni parallele)

Working tree condivisa, 3 file (`super-admin.blade.php`,
`superadmin.svg`, `negate-superadmin.svg`) riscritti 6+ volte in un
pomeriggio da sessioni concorrenti. Storia gia' raccontata in dettaglio da:
`9.5` (heroicon-shield, bug `heroicon-o-crown` inesistente catturato),
`9.6` e `superadmin-widget-crown-icons-2026-09-21` (design crown+gemma,
bug reale `@svg('modulo::svg.file')` sintassi invalida trovato e corretto),
`superadmin-widget-negate-icon-fix-2026-09-21` (regressione cerchio-slash
-> diagonale nuda). Vedi anche memoria `superadmin-widget-icon-race.md` e
`multi-agent-same-prompt-parallel-superadmin-icons.md`.

## Stato committato che ha vinto la race

Commit `eda65a161` (altra sessione, gia' su `dev` prima di questo giro):
2 SVG custom, stessa corona (`M12 3l7 3v5c0 4.5-3 8-7 10-4-2-7-5.5-7-10V6l7-3z`,
`viewBox 24`), animazione CSS nativa rispettosa di
`@media (prefers-reduced-motion: no-preference)`:
- `superadmin.svg` (attivo): scintilla (`.u-sa-spark`) pulsante scale+opacity
- `negate-superadmin.svg` (rinunciato): corona opaca al 45% + riga diagonale
  disegnata via `stroke-dasharray`/`stroke-dashoffset` animato

Design valutato buono (outline, accessibile, "fun" senza loop perenne
invasivo) — non riscritto, adottato cosi' com'e'.

## Bug reale trovato e corretto in questo giro (non nel design SVG)

Dopo il commit `eda65a161`, un'ulteriore riscrittura concorrente **non
committata** aveva rotto il widget a un livello piu' profondo delle icone:

1. `Modules/User/app/Filament/Widgets/Profile/SuperAdminWidget.php`: la
   property `public ProfileContract $profile` era stata sostituita con un
   metodo `getViewData(): array`. `XotBaseWidget` **non ha un `render()`
   custom** che chiami un hook simile — Livewire espone alla vista solo le
   property `public` del componente. Risultato: `$profile` inesistente in
   `super-admin.blade.php`, `isset($profile)` sempre falso, **widget
   interamente invisibile** (non solo le icone).
2. `super-admin.blade.php`: `icon="super-admin"` / `icon="negate-superadmin"`
   avevano perso il prefisso `user-` del set blade-icons registrato da
   `XotBaseServiceProvider::registerBladeIcons()` (prefix = nome modulo
   minuscolo, qui `user`). `BladeUI\Icons\Factory::splitSetAndName()` legge
   tutto prima del primo `-` come prefix: senza `user-`, la ricerca cadeva
   sul set `default` (vuoto in questo progetto) -> `SvgNotFound` silenziosa
   a runtime (fallback globale vuoto in `config/blade-icons.php`).

Confermato **non** un problema di registrazione set (verificato via
`app(BladeUI\Icons\Factory::class)->all()`: set `user` presente, prefix
`user`, path `Modules/User/resources/svg`) ne' di contenuto SVG (`svg()`
grezzo risolveva entrambe le icone) — il bug era a monte, nel binding
Livewire e nel nome icona passato al component.

## Fix

`Modules/User/app/Filament/Widgets/Profile/SuperAdminWidget.php`: ripristinata
`public ProfileContract $profile`, valorizzata in `mount()`; rimosso
`getViewData()` (dead code, mai invocato). `super-admin.blade.php`:
`icon="user-superadmin"` / `icon="user-negate-superadmin"`.

Rimossi 6 file SVG orfani in `Modules/User/resources/svg/` (nomi di tentativi
intermedi mai referenziati: `negate-super-admin.svg`, `super-admin-active.svg`,
`super-admin-negated.svg`, `super-admin.svg`, `user-negate-super-admin.svg`,
`user-super-admin.svg`).

## Verifica

- `app(Factory::class)->svg('user-superadmin')` / `svg('user-negate-superadmin')`:
  risolvono, contenuto non vuoto.
- `Livewire::test(SuperAdminWidget::class)` con setup reale (ruolo, profilo,
  pannello Filament): `assertSeeHtml('data-super-admin-state="active|negated"')`
  **+ nuova asserzione `assertSeeHtml('<svg')`** aggiunta ai 2 test di
  visibilita' (prima non c'era, motivo per cui la regressione era passata
  inosservata ai test pur rompendo il rendering reale).
- `php artisan test` sui 2 file di test del widget: **12 passed (33 assertions)**.
- PHPStan su `SuperAdminWidget.php`: 0 errori.
- Commit: `2d91c521f`.

## Lezione

Un test che asserisce solo su un attributo custom (`data-super-admin-state`)
puo' restare verde anche quando il contenuto reale (l'icona SVG) e' sparito,
se quell'attributo e' scritto a mano nel blade indipendentemente dal
rendering dell'icona. La riga di guardia utile era `assertSeeHtml('<svg')`,
non presente prima di questo giro. Vedi anche
[[guard-test-beats-code-reading-multiagent]],
[[missing-import-fatal-cascades-whole-panel]] (stesso pattern: un pezzo
mancante silenzioso rompe il rendering di un intero componente Livewire/Filament,
non solo il dettaglio che sembrava in gioco).

## Addendum 2026-09-21 (turno successivo): root cause reale "icone non si vedono"

Dopo il commit `2d91c521f` sopra, un'ULTERIORE riscrittura concorrente (non
mia, gia' in working tree quando ho ripreso il task) ha di nuovo cambiato
`SuperAdminWidget.php`: `$view` ora punta a `super-admin-toggle.blade.php`
(non piu' `super-admin.blade.php`), `$profile` di nuovo via `getViewData()`
invece di property public + `mount()`.

**Correzione alla diagnosi della sezione precedente**: `getViewData()` NON
e' dead code per un Filament Widget. `Filament\Widgets\Widget::render()`
(vendor, non override) e':
```php
public function render(): View {
    return view($this->view, $this->getViewData());
}
```
Chiama `getViewData()` esplicitamente — a differenza di un componente
Livewire generico, qui funziona sempre, a prescindere da property public.
L'ipotesi "Livewire espone solo property public" nella sezione precedente
era sbagliata per questo caso (Widget la sovrascrive).

**Root cause reale della "invisibilita'" originale segnalata dall'utente**:
non risoluzione icone (SvgNotFound), non binding Livewire — ma **CSS**. Il
pannello User (`AdminPanelProvider extends XotBasePanelProvider`) non
registra nessun `->viteTheme()` / `FilamentAsset::register(Css::make(...))`
in tutta la catena (grep verificato). Il pannello serve quindi SOLO il CSS
prebuilt di Filament (`vendor/filament/filament/dist/theme.css`, 613KB,
minificato). Un primo tentativo di fix (round precedente a `2d91c521f`,
mai arrivato committato per via della race) usava un `<button>` con classi
Tailwind arbitrarie a mano (`text-amber-400`, `drop-shadow-[0_0_8px_...]`,
`h-7 w-7`, `hover:bg-amber-950/30`): verificato via grep sul CSS compilato,
**zero occorrenze** di tutte queste classi — non esistono nel CSS servito,
quindi l'icona non aveva ne' colore ne' dimensione ne' effetti, di fatto
invisibile o comunque non riconoscibile.

Il fix corretto (quello arrivato a convergenza, gia' in `2d91c521f` e
confermato in questo giro) e' esattamente quanto i due doc Filament
richiesti dall'utente insegnano:
https://filamentphp.com/docs/5.x/styling/icons e
https://filamentphp.com/docs/5.x/components/icon-button — usare
`<x-filament::icon-button icon="user-superadmin" color="warning" size="sm">`
invece del `<button>`+classi-a-mano. Le classi che questo componente genera
(`fi-icon-btn`, `fi-icon`, `fi-size-sm`, `fi-color-warning`/`fi-color-danger`)
**sono presenti nel CSS prebuilt** (verificato via grep: `fi-icon-btn` 56
occorrenze, `fi-size-sm` 19, `fi-color-warning`/`fi-color-danger` presenti),
perche' sono classi del framework Filament stesso, non della build Tailwind
dell'app. Stesso pattern gia' in uso con successo altrove nel repo:
`Modules/Notify/resources/views/livewire/database-notifications-trigger.blade.php`.

**Pulizia in questo giro**: rimosso `super-admin.blade.php` (duplicato morto
byte-per-byte di `super-admin-toggle.blade.php`, mai referenziato da `$view`
dopo l'ultima riscrittura). Corretto `SuperAdminWidgetTest.php`: l'asserzione
"resolves to view" usava `Modules\Xot\Actions\View\GetViewByClassAction`, che
risolve il nome vista per CONVENZIONE dal nome classe (`super-admin`),
indipendente dalla property `$view` effettivamente usata da
`Widget::render()` — passava solo perche' il duplicato morto esisteva al
path convenzionale. Riscritta per leggere `$view` via reflection (cio' che
davvero conta a runtime) e per asserire sul contenuto della vista live
(`x-filament::icon-button` + icone corrette). Verifica: `generate_icon_html()`
via tinker produce `<svg class="fi-icon fi-icon fi-size-md" ...>` con markup
completo. 6/6 Pest, PHPStan level 10 pulito su widget+test. Commit
`ebb1e13be`.

**Lezione aggiuntiva**: un pannello Filament senza `->viteTheme()` custom
non compila NESSUNA classe Tailwind ad-hoc usata nei blade dell'app — solo
le classi `fi-*`/color-config del framework. Qualunque blade Filament che
usa `text-*`, `bg-*`, `drop-shadow-[...]` scritti a mano va verificato contro
il CSS compilato effettivamente servito, non assunto funzionante solo perche'
la sintassi Tailwind e' valida.
